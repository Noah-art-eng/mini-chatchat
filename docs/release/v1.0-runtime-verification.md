# Mini ChatChat v1.0 Runtime Verification

## Scope

This report records the Phase 11.1 real Docker runtime verification for Mini ChatChat.

The goal was to prove that the project can build, start, serve the React frontend through nginx, proxy API requests to FastAPI, persist runtime data, and recover from backup on a local Docker runtime.

No RAG, Agent, MCP, Knowledge, OAuth, authentication flow, or API contract changes were made except deployment-required fixes discovered during runtime validation.

## Deployment Fixes From Runtime Validation

### MCP Import Failure

The backend container initially failed on import:

```text
NameError: name 'ToolSpec' is not defined
```

Fix:

- Added postponed annotation evaluation in `backend/services/mcp_registry.py`.

Reason:

- This was a runtime-only import failure caused by an annotation referencing `ToolSpec` before runtime import.

### Runtime Upload Directory

After moving production runtime paths under `./runtime/prod`, `/health/deps` reported `uploads_dir=error`.

Fix:

- `backend/app.py` now creates `DATA_DIR` and `UPLOADS_DIR` at startup using the configured environment paths.

### Production Runtime Layout

Production compose previously used Docker named volumes for data/uploads and a bind mount for the SQLite runtime directory. That made local backup scripts unable to cover the whole production runtime from the project directory.

Fix:

- `docker-compose.prod.yml` now uses one bind-mounted runtime root:

```text
./runtime/prod:/app/backend/runtime
```

Runtime paths:

```text
/app/backend/runtime/mini.db
/app/backend/runtime/data
/app/backend/runtime/uploads
/app/backend/runtime/model_cache
```

This keeps backup and restore explicit and inspectable for a single-host deployment.

## Backup And Restore Drill

Backup command:

```bash
MINI_CHATCHAT_DB_PATH=runtime/prod/mini.db \
MINI_CHATCHAT_DATA_ROOT=runtime/prod/data \
MINI_CHATCHAT_UPLOADS_DIR=runtime/prod/uploads \
scripts/backup.sh
```

Backup archive:

```text
backups/mini-chatchat-20260804T143640Z.tar.gz
```

Restore drill:

1. Stopped production compose.
2. Moved `runtime/prod` to a `runtime/prod.before-restore-*` directory.
3. Recreated empty `runtime/prod`.
4. Ran `scripts/restore.sh` against the backup archive.
5. Restarted production compose.
6. Checked `/api/health/deps`.
7. Logged in with the runtime verification user.
8. Confirmed the test conversation existed.

Result:

- Restore completed successfully.
- Health returned `ok`.
- User login worked after restore.
- Conversation data was restored.

## Health And Observability

Health:

- `/api/health`: includes status, service, version, provider, uptime, started time, environment.
- `/api/health/deps`: public production response includes status and dependency checks only by default. Runtime metadata, model summary, and stats require an authenticated user with Developer Mode permission or `HEALTH_DEPS_PUBLIC_DETAILS=true`.

Request ID:

- API responses include `x-request-id`.
- Backend access logs include `request_id`, method, path, status code, and duration.

Log safety:

- Backend log scan found no obvious JWT, password, refresh token, cookie, client secret, API key, Authorization, or Bearer token strings.
- Third-party libraries still emit non-JSON HTTP download logs for Hugging Face model files. These do not contain secrets, but they are not structured JSON.

## Guest Refresh Noise

Issue:

- Guest first load previously attempted `/auth/refresh`, producing browser console 401 failed-resource noise.

Fix:

- Frontend now stores a local non-secret auth session hint after successful login/register/refresh.
- First-time guests without a session hint do not call `/auth/refresh`.
- Backend still returns 401 for invalid refresh attempts.

Browser QA result:

- Production page loaded at `http://127.0.0.1/chat`.
- Playwright console check reported `0` errors and `0` warnings after the fix.

## Security Validation

Verified:

- Production cookie is `HttpOnly`, `Secure`, `SameSite=lax`, and path-scoped to `/auth`.
- Unknown Origin is rejected with `403`.
- CORS is explicit in production configuration.
- Production startup rejects weak default auth secret.
- Production startup requires `AUTH_COOKIE_SECURE=true`.
- Docker image excludes `.env`, `.env.production`, `backend/.env`, runtime data, uploads, SQLite, backups, and caches.

Important limitation:

- Local production verification used HTTP `127.0.0.1` with `Secure` cookies. Real browser cookie persistence for refresh sessions requires HTTPS in production.

## Known Issues

- Backend image is large at about `2.03GB`.
- Production compose runtime uses local bind mounts, suitable for single-host deployments but not multi-node orchestration.
- Full production LLM path was not verified inside Docker because no real API key was written to `.env.production`.
- HTTPS termination is not included in compose; it must be provided by an outer proxy or hosting platform.
- OAuth callback verification with real Google/GitHub provider credentials was not performed in this local runtime drill.
- Third-party Hugging Face model initialization logs are not JSON structured.
- Frontend JS and CSS should be optimized in a later route-splitting and legacy CSS cleanup phase.
- Resolved in Phase 11.2: frontend production and full npm audits return zero vulnerabilities.

## Production Deployable Decision

Decision: conditionally deployable for a single-host portfolio or private demo deployment.

Mini ChatChat is now proven to build and run in Docker, serve through nginx, proxy API requests, persist runtime data, recover from backup, pass health checks, pass frontend quality gates, and pass the 30-script smoke runner against the current backend.

It should not be considered fully public-production-ready until the remaining production items are completed:

- real HTTPS
- real production LLM key
- real Google/GitHub OAuth callback verification
- dependency audit review
- log rotation and monitoring
- backup encryption and off-host copy
- image size optimization
